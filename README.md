# Product Matcher

Автономный HTTP-сервис на Python 3.12 + FastAPI для сопоставления сообщения покупателя с товаром из каталога.

Сервис рассчитан на запросы в свободной форме: с опечатками, сокращениями, словоформами и лишними словами. Интернет, внешние API, LLM и внешние модельные файлы не используются.

Для поиска кандидатов применяется character n-gram TF-IDF из `scikit-learn`. Точные характеристики товара — размеры, модели, маркировки, единицы измерения и другие структурные признаки — проверяются отдельно.

Главный приоритет — минимизация ложных `matched`. Если уверенности недостаточно, сервис предпочитает вернуть `ambiguous` или `not_found`, а не уверенно указать неправильный товар.

## Как запустить

Требуется:

* Python 3.12;
* `make`.

Установка зависимостей и запуск сервиса выполняются одной командой:

```bash
make run
```

После запуска:

```text
POST http://localhost:8000/match
```

Swagger UI:

```text
http://localhost:8000/docs
```

Пример:

```bash
curl -X POST http://localhost:8000/match \
  -H 'Content-Type: application/json' \
  -d '{"messages":["саморезы по дереву 4.2 на 75, пачку"]}'
```

Тесты:

```bash
make test
```

## Решение и компромиссы

### Character n-gram TF-IDF

Пользователь редко пишет название товара точно так же, как оно хранится в каталоге. В сообщениях встречаются опечатки, окончания, сокращения, перестановки и дополнительные слова.

Поэтому для первого этапа поиска используется TF-IDF по символьным n-граммам.

Он сохраняет похожесть между строками вроде:

```text
саморез
саморезы
самарез
```

без необходимости перечислять вручную все словоформы.

TF-IDF-матрица строится один раз при старте приложения. Для текущего каталога из 466 товаров полный sparse cosine retrieval достаточно дешёвый по CPU и памяти.

### Почему одного similarity недостаточно

Высокая текстовая похожесть ещё не означает, что товары взаимозаменяемы:

```text
саморез 4.2x70
саморез 4.2x75
```

Поэтому matching состоит из двух частей:

1. TF-IDF ищет текстово похожие товары;
2. структурные признаки проверяют, действительно ли кандидат совместим с запросом.

Из сообщения извлекаются, в частности:

* размеры: `4.2x75`, `20x20x2`, `6 на 110`;
* модели и маркировки: `PW-750`, `PH2`, `M10`, `P120`;
* характеристики с единицами: `1000 мм`, `12 В`, `750 Вт`;
* единица продажи;
* количество в упаковке, если оно указано явно.

Если явно указанная характеристика конфликтует с товаром, кандидат отбрасывается независимо от TF-IDF score.

Это сознательно смещает алгоритм в сторону precision.

### Нормализация и aliases

Перед поиском запрос нормализуется, чтобы разные способы записи одной характеристики интерпретировались одинаково:

```text
4.2x75
4.2х75
4.2 на 75
```

Также используется небольшой набор доменных aliases для случаев, которые невозможно вывести из символьной похожести:

```text
болгарка -> УШМ
шурик -> шуруповерт
хомуты пластиковые -> стяжка нейлоновая
наждачка -> шкурка шлифовальная
```

Морфологические варианты вроде `саморез / саморезы / саморезов` вручную не перечисляются — их достаточно хорошо покрывает character n-gram TF-IDF.

Это компромисс между полностью generic fuzzy search и большим вручную поддерживаемым словарём предметной области.

### Нетоварные сообщения

Отдельно обрабатываются запросы, которые явно не относятся к поиску товара:

```text
где находится ваш магазин
можно оплатить картой?
какой статус заказа?
```

Если отправить их сразу в retrieval, алгоритм всё равно найдёт наиболее похожий товар из каталога. Поэтому перед matching выполняется консервативная rule-based проверка нетоварных intent: адрес, режим работы, оплата, доставка, существующий заказ и т. п.

Такие сообщения сразу получают `not_found`.

Это сделано в соответствии с основным требованием задания: false positive хуже осторожного отказа.

#### Ограничение mixed-intent

Текущая эвристика предполагает один основной intent на сообщение.

Например:

```text
где находится магазин и есть ли ПуГВ?
```

может быть целиком распознано как нетоварный запрос, хотя в нём есть товарная часть.

Для тестового это осознанное ограничение: в production я бы сначала разделял сообщение на intent/смысловые фрагменты либо использовал multi-intent classification, а product matcher запускал только для товарной части.

### Статусы

`matched` возвращается только при достаточно высоком score и заметном преимуществе первого кандидата над остальными.

`ambiguous` возвращается, если несколько товаров выглядят правдоподобно и безопасно выбрать один нельзя. В ответ попадают 2–3 кандидата.

`not_found` возвращается, если подходящего товара нет, запрос нетоварный, структурные характеристики конфликтуют или similarity недостаточно высока.

Пороги намеренно консервативные: высокая precision для `matched` важнее максимального recall.

### Confidence

`confidence` находится в диапазоне `0..1`, но не является статистически откалиброванной вероятностью.

Это ranking score текущего алгоритма. Например:

```json
{"sku": "SKU-123", "confidence": 0.87}
```

не означает математическую вероятность правильного ответа 87%.

Для вероятностной интерпретации потребовался бы отдельный размеченный validation set и калибровка.

## Рассмотренные альтернативы

### Чистый fuzzy matching

Хорошо работает с опечатками, но опасен для почти одинаковых товаров, различающихся размером, моделью или другой точной характеристикой.

Поэтому fuzzy similarity без структурной проверки не использовался как финальный критерий.

### Word-level TF-IDF

Хуже переносит опечатки и русскоязычные словоформы: ошибка может полностью превратить токен в неизвестное слово.

Character n-grams деградируют мягче.

### Embeddings / локальная LLM

Могли бы лучше понимать семантически разные формулировки, но для каталога из нескольких сотен товаров существенно увеличили бы зависимости, размер окружения и требования к ресурсам.

При этом embeddings или LLM всё равно не заменяют детерминированную проверку размеров, моделей и других точных характеристик.

Для текущего задания это было бы неоправданным усложнением.

## Что сознательно не сделано

В рамках тестового не добавлялись:

* PostgreSQL;
* Docker;
* авторизация;
* frontend;
* отдельный search engine;
* ML intent classifier;
* автоматическое обучение thresholds;
* полноценный multi-intent parsing.

Каталог загружается в память при старте приложения.

Thresholds подобраны вручную и консервативно. Для корректного автоматического выбора порогов нужен отдельный размеченный validation set; подбирать их статистически на нескольких десятках предоставленных примеров означало бы фактически переобучиться под тестовые сообщения.

### Почему архитектура минимальная

Для одного endpoint, локального каталога и одной бизнес-задачи я сознательно не добавлял Clean/Onion Architecture, DI-контейнеры и отдельные repository/use-case слои.

При ожидаемом объёме работы 4–6 часов это увеличило бы количество кода без практической пользы.

При этом ответственность разделена между HTTP-слоем, API-схемами, загрузкой каталога, нормализацией и matching-логикой, поэтому основные части можно независимо тестировать и изменять.

Если бы появились PostgreSQL, несколько retrieval-механизмов, обновление каталога, внешние интеграции и дополнительная бизнес-логика, тогда имело бы смысл выделить полноценные application/domain и infrastructure слои.

## Тесты

Тесты написаны на `pytest`:

```bash
make test
```

Проверяются:

* однозначные `matched`;
* опечатки и разговорные названия;
* aliases;
* недостаточно конкретные `ambiguous`;
* отсутствие товара;
* нетоварные сообщения;
* конфликтующие размеры и характеристики;
* случаи, где высокая текстовая похожесть не должна приводить к неправильному `matched`;
* HTTP request/response validation.

Отдельный акцент сделан на негативных сценариях и false positive.

## Что сделал бы до production

В первую очередь собрал бы размеченные реальные запросы пользователей с правильными SKU и ожидаемыми статусами.

На отдельном validation set измерял бы:

* precision для `matched`;
* recall;
* false positive rate;
* top-k retrieval recall;
* долю `ambiguous` и `not_found`.

После этого thresholds можно было бы подбирать по данным, а при необходимости откалибровать `confidence`.

Rule-based intent detection дополнил бы или заменил классификатором, поддерживающим mixed-intent сообщения.

Также добавил бы:

* structured logging и request/correlation ID;
* latency и status metrics;
* причины отбрасывания кандидатов;
* ограничения размера запросов и rate limiting;
* версионирование поискового индекса и атомарное переключение версии при обновлении каталога.

# Масштаб: 2 млн товаров, PostgreSQL, 50 магазинов

Текущий подход с хранением всего каталога в памяти и сравнением запроса со всеми товарами рассчитан на несколько сотен позиций.

При 2 млн товаров основной принцип matching можно сохранить, но retrieval должен стать двухэтапным:

```text
query
  |
  v
нормализация + извлечение характеристик
  |
  v
candidate retrieval
  |
  v
десятки / сотни кандидатов
  |
  v
structural filtering + reranking
  |
  v
matched / ambiguous / not_found
```

## Multi-tenancy

PostgreSQL стал бы source of truth.

Каждый товар принадлежал бы магазину:

```text
store_id
sku
name
unit
price
...
```

`store_id` обязательно участвовал бы в retrieval и индексах.

Поиск должен сразу выполняться внутри каталога конкретного магазина, а не сначала по всем двум миллионам товаров с последующей фильтрацией.

Сам `store_id` необязательно добавлять в body `/match`: в реальной системе он может определяться из authentication/API key, hostname или gateway context.

## Структурированные характеристики

Размеры, модели и другие важные параметры при таком объёме лучше хранить отдельно от текстового `name`:

```text
store_id
sku
product_type
brand
model
diameter
length
voltage
power
unit
...
```

Это позволяет дешёво отфильтровать заведомо неподходящие товары ещё до текстового ranking.

Например, для:

```text
бур sds 10x210
```

сначала можно ограничить выборку по магазину, типу, диаметру и длине, а similarity считать уже по небольшому candidate set.

## Candidate retrieval

Для первого этапа использовал бы комбинацию:

* `store_id`;
* точных моделей и артикулов;
* структурных признаков;
* PostgreSQL Full Text Search;
* `pg_trgm`;
* B-tree / GIN / GiST индексов в зависимости от типа поля.

Задача retrieval — не принять финальное решение, а быстро сократить миллионы товаров примерно до top 50–200 кандидатов с высоким recall.

После этого применяется логика, аналогичная текущей: textual score + строгая проверка модели, размеров, напряжения, мощности, единицы продажи и других характеристик.

Таким образом, fuzzy retrieval отвечает за recall, а structural filtering — за precision.

## Индексы и кэш

Индексы должны учитывать tenant scope. Например, для модели практически полезнее:

```text
(store_id, model)
```

чем глобальный индекс только по `model`.

Частые запросы можно кэшировать по ключу примерно вида:

```text
(store_id, catalog_version, normalized_query)
```

Версия каталога не позволяет использовать устаревший результат после обновления данных.

## 50 магазинов

Не стал бы автоматически держать отдельный Python-process или отдельную TF-IDF-модель для каждого магазина.

Базовая архитектура была бы stateless:

```text
FastAPI instances
       |
       v
PostgreSQL / search layer
       |
       +-- store_id=1
       +-- store_id=2
       +-- ...
       +-- store_id=50
```

API можно горизонтально масштабировать, а tenant-specific данные держать в PostgreSQL/search layer и общем кэше.

Для отдельных очень крупных tenants позже можно использовать partitioning или отдельные поисковые индексы.

## Если PostgreSQL перестанет справляться

Не стал бы заранее добавлять Elasticsearch/OpenSearch только из-за двух миллионов строк.

Сначала проверил бы PostgreSQL с правильными индексами, `pg_trgm`, Full Text Search, structural pre-filtering и кэшированием.

Если на реальной нагрузке он перестанет удовлетворять требованиям по p95/p99 latency, throughput или качеству retrieval, candidate retrieval можно вынести в OpenSearch/Elasticsearch, оставив PostgreSQL source of truth.

При необходимости embeddings также можно добавить как дополнительный semantic retrieval signal, но не как замену структурной проверке.

Итого при масштабировании меняется прежде всего способ получения небольшого candidate set. Основной принцип решения остаётся тем же: неточный поиск обеспечивает recall, а окончательное решение принимается консервативно с учётом точных характеристик товара.
