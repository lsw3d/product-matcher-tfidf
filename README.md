# Product Matcher

Автономный HTTP-сервис на Python 3.12 + FastAPI, который сопоставляет свободный текст покупателя с локальным каталогом. Приоритет — минимум ложных `matched`: при недостаточной уверенности сервис возвращает `ambiguous` или `not_found`.

## Как запустить

Нужны Python 3.12 (подойдёт и новее) и `make`. Установка зависимостей в локальный `.venv` и запуск выполняются одной командой:

```bash
make run
```

После запуска доступны:

- `POST http://localhost:8000/match`
- Swagger UI: `http://localhost:8000/docs`

Пример:

```bash
curl -X POST http://localhost:8000/match \
  -H 'Content-Type: application/json' \
  -d '{"messages":["саморезы по дереву 4.2 на 75, пачку"]}'
```

Тесты:

```bash
make test
```

После установки сервис работает без интернета, внешних API, LLM и ключей.

## Решение и компромиссы

### Алгоритм

```text
сообщение
  -> нормализация и извлечение характеристик
  -> character n-gram TF-IDF retrieval
  -> проверка семейства и содержательных слов
  -> hard constraints
  -> rerank со штрафом за необъяснённые слова
  -> matched / ambiguous / not_found
```

Character n-grams устойчивы к небольшим опечаткам и словоформам (`саморез`, `саморезы`, `самарез`). Матрица каталога строится один раз при старте; для ~500 товаров полный поиск по ней достаточно дешёвый.

Одна текстовая похожесть небезопасна: названия `саморез 4.2x70` и `саморез 4.2x75` близки, но обозначают разные позиции. Поэтому TF-IDF только находит кандидатов, а финальное решение проверяет их структурные признаки.

### Структурные признаки

Из запроса и каталога извлекаются:

- размеры (`4.2x75`, `20x20x2`, `6 на 110`);
- модели и маркировки (`PW-750`, `PH2`, `M10`, `P120`);
- величины с единицами (`1000 мм`, `12 В`, `750 Вт`);
- назначение, цвет и другие значимые qualifiers;
- единица продажи и количество в упаковке.

Явный конфликт отбрасывает кандидата независимо от similarity: `M10` не становится `M8`, а сантиметры — миллиметрами. Отдельные длины сравниваются в эквивалентных единицах (`1 м = 100 см = 1000 мм`), если речь идёт о характеристике SKU, а не объёме заказа.

Семейство товара выводится по первому содержательному слову названия каталога. Это не даёт запросу `гвоздь 6x60` превратиться в `дюбель-гвоздь 6x60`, а запросу только по свойству — доказать тип товара.

Маркировки покупатель нередко набирает кириллицей, причём по разным правилам: в `р120` буква `р` — это латинская `p` по начертанию, а в `ТР-750` — транскрипция `tr`. Одной таблицей это не покрывается, поэтому код разворачивается в набор прочтений, и коды считаются одинаковыми при непустом пересечении наборов. В каталоге кириллица встречается тоже (`Арсенал-Т АРС-230`), так что правило работает в обе стороны.

### Лишние слова

Требовать, чтобы каждое слово запроса нашлось в названии товара, нельзя: покупатель пишет `подскажите`, `самовывоз`, `в бухте`. Игнорировать всё подряд тоже опасно — `дюбель бабочка` и `сверло форстнера` это другие товары. Непривязанное слово отбрасывает кандидата в двух случаях:

- каталог знает это слово, но у данного товара его нет — значит, оно противоречит товару (`саморез мебельный`, `уровень лазерный`);
- слово стоит сразу после названия семейства, то есть на месте уточнения типа (`дюбель бабочка`, `диск алмазный`). Исключение — названная маркировка: она определяет товар точнее любого слова, поэтому `отвертка крестовая PH2` остаётся отвёрткой PH2.

Отдельный случай — слово перед названием семейства. Там стоит либо вежливый оборот (`посмотрите дрель`), либо вершина словосочетания, то есть сам предмет разговора (`унитаз подвесной`, `напильник круглый`). Без морфологии их не различить, а список вежливых слов заведомо неполон, поэтому кандидат не отбрасывается, но получает такой штраф, что пережить его может только совпадение с прочими признаками. `посмотрите дрель prowerk pw-750` остаётся `matched` за счёт маркировки, а `унитаз подвесной` не превращается в `Подвес прямой`.

Остальные неизвестные слова считаются шумом: кандидат остаётся, но его score получает штраф за каждое необъяснённое слово. Так `дрель ударная prowerk pw-750 самовывоз` остаётся `matched`, а `сверло форстнера 10 мм` — `not_found`.

Отдельно решается случай, когда лидер отличается от конкурента назначением, о котором не спрашивали: `сверло 10 мм` одинаково описывает сверло по дереву, по бетону и по металлу, и отрыв лидера создаёт не запрос, а частотность слов в каталоге. Такой запрос возвращает кандидатов, а не угаданное назначение.

### Нормализация

Нормализация унифицирует регистр, `ё/е`, десятичную запятую, варианты `x/х/×`, полные и латинские обозначения единиц. Словоформы сводит лёгкий стеммер: он снимает одно самое длинное русское окончание, поэтому `саморез`, `саморезы` и `саморезами` сходятся в одну основу без словаря и morphology-зависимостей. Остаток различий вроде `гайки` / `гаек` добирает проверка на одну правку, она же прощает опечатки (`перфаратор`, `пирчатки`). Для коротких основ фаззи-сравнение отключено: иначе `дела` сошло бы за опечатку в `дрель`.

Небольшой набор предметных aliases покрывает формулировки, которые ненадёжно выводить только из similarity:

```text
болгарка -> УШМ
шурик -> шуруповерт
проф труба -> труба профильная
хомуты пластиковые -> стяжка нейлоновая
наждачка -> шкурка шлифовальная
круг отрезной / лепестковый -> диск отрезной / лепестковый
```

Также удаляется ограниченный разговорный шум (`мне нужна`, `у вас есть`, `для дома`, подписи характеристик). Точные модели, размеры и назначения шумом не считаются.

### Нетоварные сообщения и статусы

Отсекаются явные запросы про адрес, режим работы, оплату, доставку, возврат и статус заказа. Но этот фильтр не перебивает названный товар: `когда доставите кабель?` — не заказ, а `кабель ВВГнг 3х1.5 с доставкой` — вполне, поэтому проверка пропускается, если в сообщении есть размер, код или величина с единицей. Mixed-intent сообщение без таких признаков (`где находится магазин и есть ли ПуГВ?`) по-прежнему целиком получает `not_found`: для тестового это осознанный компромисс в пользу precision.

- `matched` — высокий score и достаточный отрыв лидера; уникальное точное название также считается достаточным.
- `ambiguous` — 2–3 близких правдоподобных кандидата.
- `not_found` — товар отсутствует, запрос нетоварный или признаки конфликтуют.

`confidence` — ranking score в диапазоне `0..1`, а не откалиброванная вероятность. Для вероятностной интерпретации нужен размеченный validation set.

### Что пробовал и отбросил

- Чистый fuzzy matching даёт опасные совпадения близких моделей и размеров.
- Word-level TF-IDF хуже переносит опечатки и русские словоформы.
- Embeddings или локальная LLM добавили бы зависимости и ресурсы, но не заменили бы проверку точных характеристик.
- Полноценная морфология (`pymorphy`) ради нескольких словоформ — лишняя зависимость: усечения окончаний хватает, а спорное добирает проверка на одну правку.
- Требование «каждое слово запроса должно найтись в названии» выглядит безопасным, но превращает в `not_found` любое живое сообщение с лишним словом — ровно то, что просит распознавать ТЗ.

### Где осознанный оверинжиниринг

По объёму кода решение заметно больше минимального — это осознанный выбор: архитектуру я не раздувал, но алгоритм сделал тяжелее, чем «fuzzy по названию + пороги», потому что в ТЗ главное — не выдавать ложный `matched`, даже если из‑за этого чаще приходится отвечать `ambiguous` или `not_found`.

Что выглядит избыточным для тестового и почему всё равно оставлено:

- **`normalization.py` (~640 строк)** — десятки regex-словарей (aliases, qualifiers, шум, homoglyphs, транскрипции кодов). Для каталога из ~500 позиций это уже тюнинг под конкретный hardware-ассортимент, а не базовый скелет. Без части этих правил живые формулировки (`болгарка`, `р120`, `унитаз подвесной`) начинают давать false positive или пропуск товара — то, против чего ТЗ предупреждает явно.
- **Логика шумных слов в `matcher.py`** (`_count_noise_tokens`, `head_conflict`, family anchoring) — тонкая и хрупкая; проще было бы чаще отдавать `ambiguous` одним порогом. Но ТЗ просит разбирать сообщения с лишними словами, а жёсткое «каждое слово должно совпасть» ломает как раз живой язык. Отдельные штрафы и исключения — компромисс между этими двумя требованиями.
- **`scikit-learn` для ~500 позиций** — зависимость тяжелее, чем `difflib` / `rapidfuzz`. Char n-gram TF-IDF выбран за устойчивость к опечаткам и словоформам при полном проходе по каталогу; для такого размера это не нужно ради скорости, а ради качества retrieval до structural checks.
- **~340 тестов, включая прогон по всему каталогу** — для объёма «4–6 часов» из ТЗ многовато. Зато там же требуются негативные сценарии и проверка на сообщениях вне `messages.txt`; без held-out набора и каталожных регрессий сложно доказать, что precision не куплена подгонкой под примеры.

Упростить matcher и normalization можно было бы заметно быстрее, но тогда пришлось бы сильнее полагаться на similarity и чаще рисковать ложным `matched` на близких SKU — прямо против ключевого требования ТЗ.

### Что сознательно не сделано

Не добавлялись PostgreSQL, Docker, авторизация, frontend, отдельный search engine, ML intent classifier, DI-контейнер и Clean/Onion Architecture. Для одного endpoint они не решают задачу и увеличивают объём.

Ответственность разделена без дополнительных слоёв:

```text
app/main.py           HTTP и lifecycle
app/schemas.py        API contract
app/catalog.py        загрузка каталога
app/normalization.py  нормализация и признаки
app/matcher.py        retrieval, filtering и ranking
```

Известные ограничения, оставленные осознанно:

- одно сообщение — один товар: перечисление (`саморезы 3.5х45 и дюбель-гвоздь 6х60`) вернёт `not_found`, потому что формат ответа не предполагает нескольких позиций на сообщение;
- единица продажи из запроса — жёсткое ограничение: `2 упаковки перчаток` дадут `not_found`, поскольку перчатки продаются парами. Ошибиться единицей хуже, чем переспросить;
- словари разговорных синонимов, служебных слов и qualifiers конечны и подобраны по этому каталогу; на другом ассортименте их пришлось бы пересобирать, и это первое, что заменил бы обучаемый на логах слой;
- ограничений на размер batch и длину сообщения нет.

### Тесты и путь до production

`pytest` проверяет `matched`, `ambiguous`, `not_found`, API-контракт, все точные названия каталога, опечатки, aliases, конфликтующие размеры/модели/единицы, неизвестные подтипы, нетоварные запросы и некорректные данные CSV. Основной акцент — negative scenarios и защита от false positive.

Кейсы в `tests/test_matcher.py` писались вместе с правилами, поэтому по ним нельзя судить о поведении на новых формулировках. Для этого есть отдельный held-out набор `tests/test_generalization.py`: вежливые многословные обращения, лишние слова, кириллические маркировки, падежные формы, товар вместе с вопросом про доставку и запросы о товарах, которых в каталоге нет, но их название пересекается с каталожным (`унитаз подвесной`). Пороги по нему не подбирались.

До production потребовались бы:

- размеченный набор реальных запросов и метрики precision/recall/FPR/top-k recall;
- подбор thresholds на отдельном validation set и при необходимости калибровка confidence;
- structured logging, correlation ID, latency/status metrics и причины отбрасывания;
- лимиты batch/request, rate limiting и безопасное версионирование каталога.

## Масштаб: 2 млн товаров, PostgreSQL, 50 магазинов

Полный проход по in-memory TF-IDF рассчитан на небольшой каталог. При 2 млн позиций retrieval стал бы двухэтапным:

```text
query
  -> normalization / structured features
  -> indexed candidate retrieval
  -> top 50-200
  -> structural filtering + reranking
  -> result
```

PostgreSQL был бы source of truth. Каждая позиция содержала бы `store_id`, а tenant scope обязательно входил бы в запросы и индексы:

```text
store_id, sku, name, unit, price,
product_type, brand, model, structured attributes...
```

Размеры, модель, напряжение и другие характеристики хранились бы отдельными полями для дешёвого pre-filtering. Поиск сразу ограничивался бы каталогом нужного магазина; `store_id` мог бы приходить из API key, hostname или gateway context, не меняя body `/match`.

Для candidate retrieval сначала достаточно возможностей PostgreSQL:

- B-tree по точным полям и composite indexes с `store_id`;
- Full Text Search;
- `pg_trgm` + GIN/GiST для fuzzy retrieval;
- exact lookup по SKU/model до fuzzy поиска.

Частые результаты можно кэшировать по `(store_id, catalog_version, normalized_query)`. API-инстансы остаются stateless и масштабируются горизонтально. Если PostgreSQL перестанет удовлетворять требованиям по latency/throughput, retrieval можно вынести в OpenSearch/Elasticsearch, сохранив PostgreSQL как source of truth и текущий structural rerank.
